# Reference selection and numerical contract

For an extension, start from the existing case's reference and calibration;
read only the sections affected by the change. A first case needs reference
selection and calibration. Keep its contract near the model case rather than
introducing a generic configuration system.

## Choose the comparison that proves the claim

| Claim | Reference | What a pass establishes |
|---|---|---|
| Native implementation parity | Pinned trusted Diffusers or official implementation with the same weights | Numerical fidelity for this workload and configuration |
| Acceleration, cache, or quantization accuracy | A trusted native baseline with the feature disabled, with checkpoint/request fixed | Fidelity of that feature relative to the named baseline |
| Online/offline consistency | The same implementation through the other API path | Request translation and output-path consistency |
| Regression against a golden | Frozen artifacts generated by a trusted reference, with provenance | Fidelity to that specific reference contract |

A Diffusers-backend-vs-Diffusers comparison does not validate the native
pipeline. For an accelerated candidate whose changes also affect the default
path, preserve a known-good baseline revision or artifacts; disabling a flag
in the changed implementation may not isolate the change. If the baseline's
upstream fidelity is unverified, state that limitation rather than upgrading
the claim to official parity.

Choose a reference strategy based on dependencies, runtime cost, and control:

- **Live Diffusers:** suitable when a matching pipeline exists and fits the
  test environment. Pin and record the actually imported package version or
  source commit and resolved path, especially when `PYTHONPATH` overrides it.
- **Official runner in an isolated environment:** suitable for an independent
  implementation with incompatible dependencies. Pin its repository commit
  and dependencies. Pass the same serialized request to separate workers;
  retain outputs, metadata, logs, and exit status. Do not add reference-only
  dependencies to the serving runtime merely to execute the test.
- **Frozen golden:** suitable for expensive references or stable CI inputs.
  Verify model/reference revisions, request/input hashes, and artifact hashes
  before comparing. Generate separately from the candidate and version any
  replacement; CI reads the golden. Local reference generation does not imply
  authorization to publish assets or replace a canonical reference. See the
  [SANA golden contract](../../../../tests/e2e/accuracy/sana_video/README.md).

## Preflight before model loading

Use the reference worker's exact interpreter/launcher, working directory,
`PYTHONPATH`, and dependency environment. Prefer an existing import-only check
when it covers the actual pipeline and required components; `--help` is not
enough if imports occur later. Otherwise adapt this Bash template, replacing
the launcher and placeholders. It imports the class without loading weights:

```bash
<reference-python-or-launcher> - <<'PY'
import importlib
import inspect
import sys
from importlib.metadata import version

module = importlib.import_module("<reference-module>")
pipeline = getattr(module, "<pipeline-class>")
actual_version = version("<distribution-name>")
print(sys.executable, module.__file__, inspect.getfile(pipeline), actual_version)
assert "dummy_" not in pipeline.__module__, "Missing reference dependency"
assert actual_version == "<pinned-version>", actual_version
PY
```

Import required custom processors/components too. For a source checkout,
verify its actual commit and imported paths against the pinned reference;
a package version alone cannot detect a different editable checkout.
For unpackaged official source, replace the distribution-version assertion
with that commit check.
For frozen-golden comparison, validate provenance/assets without importing
the unused generating pipeline. Finish preflight with these case-specific checks:

- **Assets:** resolve expected components/configs, tokenizers and selected weight
  indexes; verify every referenced shard and required auxiliary file exists and
  is nonempty. Validate input decoding/hash and golden manifest size/hash where
  applicable. A model directory or `model_index.json` alone is insufficient.
- **Comparison environment:** import the metric dependencies and check required
  tools in the process that uses them (`ffmpeg -version` / `ffprobe -version`
  for encoded video); confirm target devices/backends are available.

Save the command, resolved versions/paths, asset checks, and exit status. Fix
failed prerequisites and rerun that check before loading either model. If they
cannot be resolved, report the blocker; a required CI gate must fail preflight
rather than succeed with a skipped comparison.

## Comparison checklist

Keep one short record: `field | reference effective value | candidate effective
value | evidence/deliberate difference`. Use only relevant rows below; the model
case supplies concrete values. Trace request translation/defaults to the actual
runtime settings or saved metadata, not just similarly named arguments.

| Area | Check on both sides |
|---|---|
| Source and inputs | Implementation/checkpoint revisions, prompt/media hash and order, preprocessing, shape/count/FPS |
| Randomness and sampling | Seed, generator device/noise dtype and draw order, scheduler/timesteps, steps and guidance |
| Numerical path | Component dtypes, actual attention backend/processors, determinism, relevant cache/quantization/parallel/offload/compile settings |
| Output and comparison | Decode settings, raw vs encoded output, range/layout/RGB(A), codec, metric implementation and aggregation |

Equal seeds need not produce equal initial noise. Share latents when supported,
or establish the actual RNG behavior and reference repeatability. Do not hide
request/output mismatches by resizing, dropping frames/layers, or truncating audio.

For an optimization comparison, change the feature under test and keep other
settings fixed. For native/upstream parity, align behavior-affecting settings
and explain unavoidable differences, including memory-management choices.

## Calibrate a scoped gate

1. **Measure reference repeatability.** Repeat the trusted reference with the
   fixed workload on the target environment. Inspect unexpected variation
   before attributing any difference to vLLM-Omni.
2. **Collect a known-good comparison.** Measure a trusted baseline against
   that reference. Save per-case/per-frame results and the environment. A
   known-good result can come from existing CI evidence when its contract
   matches; another model's threshold cannot establish this calibration.
3. **Recommend metrics and margins.** Select error/similarity metrics appropriate
   to the representation. Derive a tolerance from observed numerical
   variation and the intended fidelity requirement. Record the calibration
   source and justification beside the threshold. Device-specific thresholds
   need device-specific evidence, not merely a failing candidate run.
4. **Judge the candidate against the fixed accepted or proposed policy.** Label
   results under a proposal as provisional. On failure, use the diagnostic
   order below. An intentionally approximate feature needs an
   explicit fidelity target and a reported tradeoff.

If calibration cannot run, implement the case and document the missing
measurements and exact commands. Any proposed numerical tolerance is
provisional; do not present it as a validated CI gate. Reuse an existing gate
without recalibration only when its model, workload, representation, and
numerical environment remain within the gate's documented scope.

Default to numerical fidelity metrics such as SSIM/PSNR, normalized pixel
error, or tensor error. Image SSIM/PSNR describe matched images, not prompt
understanding. CLIP, FID, or VBench may support a separately requested semantic
or distributional quality evaluation with a defined workload; they do not
replace native/reference parity for a single seeded case.

## Threshold recommendation and user selection

Every model handoff must recommend a threshold, including when recommending an
existing accepted gate unchanged, or explicitly explain why the available evidence
cannot justify one. Report, per metric:

- Definition, aggregation, direction, units/range, and recommended value.
- Scope: model/workload, representation, hardware, and numerical environment.
- Trusted observation range and worst value, number of independent runs/cases,
  reference repeatability, and evidence/artifact locations. Frames or pixels
  within one run are not independent repeated-run measurements.
- Headroom and why it covers observed normal variation while preserving the
  intended sensitivity to regressions. For a lower bound on a higher-is-better
  metric, headroom is `min(known-good values) - proposed bound`; for an upper
  bound on a lower-is-better metric, it is `proposed bound - max(known-good values)`.
  Match the gate's aggregation and state when sparse data cannot establish
  stability; a positive gap alone is not calibration.

When measurements are unavailable, identify any sourced engineering target as
provisional, report headroom as unknown, and list the missing measurements. If
there is no defensible numerical target, explicitly report that a recommendation
cannot yet be justified; do not invent observations or a validated margin.

Complete feasible implementation, measurements, and the reviewable proposal
before handing off the threshold decision. The user chooses the final new or
adjusted gate; an already selected, in-scope gate needs no repeated approval.
Pending selection, report `threshold proposal awaiting selection`, even if the
candidate meets the proposed bound. A later threshold-only selection can be
evaluated against saved complete metrics when the numerical contract is unchanged.

## Diagnose before rerunning

Preserve failed outputs, metrics, effective request/provenance, and logs before
changing anything. Check in this order, using saved evidence before new runs:

| Order | First check |
|---|---|
| 1. Environment and assets | Preflight results, imports/revisions, missing/corrupt weights or inputs, device/tool availability |
| 2. Request and output structure | Effective input/preprocessing, task, shape/count/channels, frame order/FPS, audio shape |
| 3. Reference repeatability | Existing repeatability evidence; repeat the trusted reference only when this remains unresolved |
| 4. Numerical path | Actual RNG, schedule/guidance, component dtypes, attention, cache and relevant execution settings |
| 5. Implementation differences | Compare the earliest relevant intermediate, such as conditioning, initial noise, denoising or VAE output |

Before each rerun record `hypothesis -> change (or controlled repeat) -> smallest
check -> expected evidence`; afterwards record the outcome. Use a fresh output
directory or archive fixed paths. Do not blindly rerun unchanged failures,
loosen thresholds, or regenerate goldens from the candidate to obtain a pass.
If no new evidence supports another check, stop retries and report the unresolved
cause and missing evidence. Keep successful results for unaffected checks.
