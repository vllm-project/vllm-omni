# Diagnosing and revisiting a candidate

State a prediction someone can falsify. For example, consuming the original layout should remove packing from eligible chunks and shorten time to first output. Align the actual route, work performed, and client or bottleneck metric for one real request or steady-state window.

| Observation | Discriminating experiment | Decision |
|---|---|---|
| Invalid control, inactive fast path, or silent fallback | Align input, deployment, and output. Count eligible requests, activations, and fallback reasons by shape. Toggle the path on a real eligible example. | Repair the control or guard. For rare shapes, check their weight in throughput or the slow tail before estimating the opportunity. |
| Path runs but predicted work persists | Compare calls, bytes, and useful rows at the replaced boundary on the same shape. Look for duplicate work, a shifted cost, or a baseline that already eliminates it. | Change one factor and predict the counter that should move. Close the mechanism for the covered workload if a sufficiently sensitive test contradicts the prediction. |
| Local saving, flat or worse service metric | Align the same request or batch. Measure packing, synchronization, waits, recomputation, and residency. Find the branch that sets completion time, the saturated resource for throughput, or the requests that determine P95. Check downstream queues. | Isolate removable overhead or gate on profitable shapes. If another stage hides the saving, record when it would become visible. Keep the cause open if evidence cannot distinguish the two. |
| Wrong output, truncation, OOM, or quality loss | Find the first divergent output, state, shape boundary, or allocation peak. Try a scoped equivalent implementation, shape fallback, or shorter buffer lifetime. Recheck failing samples and transitions. | Pause adoption. Measure performance again after the repair. Close a variant that conflicts with a hard requirement and has no viable equivalent path. |
| Gain within noise or below deployment value | Estimate exposure under the target mix. If the interval includes a useful effect, pair runs or isolate the benefiting and regressing groups, then retest the actual mix. | Defer low-upside work. Record the baseline and scope when the comparison excludes a useful gain. |

## Preserve a retest that someone can actually run

- Before screening variants, state what advances, which outputs must agree, and which loads require qualification. Record compilation, fallback, timeouts, and state carried over between arms. Even a symmetric run order can favor a candidate if only the control compiles online. Match warmup coverage for steady-state claims. A completed high-concurrency run can retain its scoped result even if an OOM at another required load disqualifies the deployment.
- If an arm label conflicts with observed behavior, align the request window with process startup, switch activation, and branch counters using full timestamps. Repeat a window that straddled a switch. A filename or startup configuration alone leaves arm identity unresolved.
- In the project's experiment record, use a searchable stage and work description. Save the baseline, local and service evidence, blocker, trigger, and minimal retest. Preserve the patch or switch, workload command, and raw result before rollback. Append later findings to the original record.
- Use observable triggers, such as a shorter codec-to-PCM queue exposing the Talker on slow requests, or graph coverage improving while ready rows still split. On the new baseline, retest candidates whose triggers match and whose potential remains material. Pause repeated tests that cannot distinguish causes.
- If B removes a blocker for candidate A, compare B with B+A to decide whether A now pays off. To claim B amplified A's benefit, also compare the old baseline with A alone. Keep other conditions comparable across the four arms and report the difference between incremental gains and its variability.
