# Choosing a candidate from bottleneck evidence

Follow one or two signals when the bottleneck is known. Scan more broadly after a model, hardware, or topology change, when local candidates stall, or when asked about blind spots. Compare existing implementations and prior experiments under compatible request semantics, stage boundaries, and resource limits.

| Direction | First observation | Candidate changes and costs |
|---|---|---|
| Repeated computation and setup | Count work per step, chunk, and request. Identify consumers and reusable reference identities. | Fold constants at load time, incrementally maintain state, skip work after termination, or amortize steps with speculation. Measure acceptance and useful frames. Cache prompts, embeddings, or conditioning only where reuse and residency justify it. |
| Operators, layout, and compilation | Find frequent small kernels, layout changes, and copies inside graphs. Identify the real backend, caller, and compilation coverage. | Batch existing operations, fuse sampling or elementwise work, pack QKV, or reuse contiguous KV slots. Compare a custom kernel with the deployed primitive on real weights. Include assembly, writeback, and numerical effects. |
| Graph replay and startup | Count capture, replay, fallback, shape frequency, and pool admissions. Separate cold startup, first occurrence, and steady state. | Fix a guard, add a missing batch, length, or offset bucket, or change admission and eviction. Charge padding, recapture, warmup, and resident memory. |
| Scheduling, batching, and replicas | Before each dispatch count actually ready rows and why identity, shape, state, or mask split them. Check downstream saturation and starvation. | Batch compatible ready rows. If identity only affects setup, condition independently and batch downstream with per-row state. Consider priority, placement, sticky routing, granularity, or a concurrency cap. Waiting to form a batch requires an arrival-rate estimate, a continuity budget, and a fairness check. |
| Data movement and synchronization | Match producer, receiver, and consumer events per request. Separate CPU work, device queueing, host/device transfers, collectives, serialization, and client delivery. | Keep host-known metadata on the host. Keep constants on device, reuse pinned buffers, coalesce transfers, or write into the destination buffer. Evaluate communication overlap and parallelism against topology, stream dependencies, ownership, and buffer lifetime. |
| Memory, capacity, and stability | Plot allocations, allocator reservations, and free device memory over time. Identify weights, graph pools, KV state, temporary copies, and fragmentation. | Reduce peak copies, reuse buffers, or manage capture admission separately from execution-time batch splitting. Test repeated runs under pressure and report completion and healthy-path overhead. |
| Deployment and load | Verify loaded code, effective configuration inside worker processes, actual placements, and eligible shapes. | Restore a valid baseline. Separate a configuration correction, activation of an existing fast path, and new code. Compare resource changes only when allowed by the workload contract. |

## Specify a falsifiable change

- For a coverage review, distinguish tested directions, directions excluded by current constraints, and unknowns. High graph replay coverage still leaves device execution, adjacent reads and writes, and redundant model invocations to investigate.
- When acceleration is expensive to implement, perturb work in the opposite direction. In one experiment, doubling diffusion steps increased low-concurrency latency. Measure call counts, output length, and queueing. Use the result to select a follow-up. Reducing steps requires its own timing and quality check.
- Name the current implementation, single change, eligible rows, first counter expected to move, and target metric. Keep shared prerequisites in both arms. Measure inseparable changes together and identify possible ablation boundaries.
- Group proposals sharing a premise. If wider batches, extra graphs, and a scheduler change all require more compatible ready rows, measure those rows once. Preserve differences in eligibility, fallback behavior, and quality risk.
- Trace a long wait to its producer. The first device-to-host read can collect outstanding device work. Time the transfer separately after the source is ready. Use interval unions within a common window to account for overlap. At steady state, throughput times CPU seconds per request estimates cores used. Throughput times residence time estimates in-flight work at the same queue boundary.
- For fewer sampling steps, skipped guidance, lower precision, or reduced context, estimate removable work and identify affected outputs and quality checks. Distinguish an engineering stopping point from coverage of a direction and a demonstrated hardware or algorithmic limit.

## Estimate the return before building

First remove all target work in a conditional estimate with fixed workload, dependencies, and scheduling. Then substitute timings from the target backend and real shapes. Include hits, misses, fallback, and new costs. For a 2 ms mean latency target, if one in four requests hits once and every request pays 0.5 ms, each hit must save at least 10 ms assuming fully exposed savings and no queueing.

| Target | Low-cost estimate |
|---|---|
| Mean latency, first packet, or RTF | Count actual calls by shape per request. For serial work use frequency times net saving. For parallel branches recompute when dependencies join. Count work before first useful output for first packet. Reaggregate all requests, including misses, and preserve the RTF denominator. |
| P95 or P99 | Construct before/after completion times for the same representative requests and take the difference of their percentiles. Requests may change rank. If only aggregate percentiles exist, collect per-request samples joined with eligibility. |
| Throughput, capacity, or queue-sensitive tails | Estimate service demand on the saturated resource per useful unit of output, then find the next limiting resource. Match device count, arrival pattern, and output accounting. If scheduling changes, first reproduce baseline behavior in replay and report error and sensitivity. Use a small real-load perturbation if the ranking is unstable. |
| Cache, capture, or precomputation | For setup cost F, saving s per hit, cost c per access, hit probability p and N accesses per lifetime, estimated net time saved is N * (p * s - c) - F. Account for restarts, eviction and recapture. When startup and request latency have separate objectives, report them separately. Check peak memory and quality independently. |

- Buy the cheapest evidence that can change the decision. Count actual hits, replay representative shapes, feed a consumer precomputed equivalent output, or try an existing switch. Preserve downstream work and dependencies. Test a fragile compatibility, quality, or capacity assumption first.
- If credible optimistic savings fall short, defer expensive integration. If an unknown dominates, solve for its break-even value and measure it. Use paired serving A/B when realistic savings are material and detectable. Improve measurement precision if a valuable effect lies below current resolution. Without a business threshold, compare plausible impact, implementation cost, and qualification cost.
- Save the forecast before running. Substitute measured hit distribution, unit savings, overlap, queueing, and overhead one at a time and recompute the target metric. Preserve unexplained differences. Update only candidates sharing the failed premise. Verify a winner selected from several variants in independent runs on held-out representative requests.
- To review exploration cost, use existing timestamps for time to the first actionable decision and device-hours to qualification on comparable tasks. Distinguish informative negative tests from repetitions that produce no new evidence. Keep version-specific thresholds with their experiments.
